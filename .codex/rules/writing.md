# Writing

Rules for technical writing, documentation, issues, pull requests, comments, and UI copy.

## Accuracy

Preserve facts.

Never invent:

- requirements;
- metrics;
- test results;
- user research;
- decisions;
- performance claims;
- limitations;
- citations.

If information is missing, say what is missing.

## Reader

Write for the actual reader.

Do not re-explain context they already have unless it is needed for the artifact to stand alone.

Put the important information early.

## Style

Prefer:

- plain words;
- concrete statements;
- active voice when clearer;
- established project terminology;
- concise sentences;
- useful detail.

Prefer `use` over `utilize`, `help` over `facilitate`, and concrete mechanisms over abstract claims.

## Signal

Every sentence should contribute information.

Remove:

- filler;
- generic introductions;
- repeated conclusions;
- corporate language;
- vague authority;
- unsupported marketing claims;
- chatbot residue.

Avoid phrases such as:

- "Great question!"
- "Of course!"
- "Let's dive in"
- "It is important to note"
- "I hope this helps"

## Structure

Do not force:

- groups of three;
- dramatic fragments;
- repeated "not X, but Y" constructions;
- excessive bold labels;
- decorative emoji;
- unnecessary title case;
- punctuation used mainly for style.

Use structure when it helps comprehension.

## Technical terminology

Use the correct technical term consistently.

Do not cycle through synonyms simply to avoid repetition.

Do not simplify terminology when precision would be lost.

## Claims

Prefer:

- mechanisms;
- observable behavior;
- measured results;
- explicit constraints.

Avoid vague claims such as "robust", "seamless", "powerful", or "scalable" unless the text explains what makes the claim true.

Use `humanizer` or `unslop` when a writing task needs a dedicated editing pass.
